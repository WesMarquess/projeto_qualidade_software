## Story

**As a** solicitante, responsável ou administrador,
**I want** telas conectadas à API para consultar salas e gerenciar solicitações de reserva,
**so that** as operações sejam persistidas e compartilhadas pelo servidor.

## Acceptance Criteria

1. **Given** a aplicação aberta, **when** o usuário seleciona Solicitante, Responsável ou Administrador, **then** a interface consulta os dados correspondentes na API do mesmo servidor.
2. **Given** a tela de Solicitante, **when** as salas são carregadas, **then** cada sala mostra do backend seu estado `DISPONIVEL`, `RESERVADA` ou `EM_MANUTENCAO`; salas indisponíveis não oferecem ação de reserva.
3. **Given** IDs cadastrados e uma sala disponível, **when** o Solicitante envia um intervalo válido, **then** a interface cria a reserva pela API e exibe a resposta persistida no servidor.
4. **Given** uma reserva do Solicitante, **when** ele consulta, altera o horário ou cancela, **then** a interface usa as rotas existentes da API, atualiza os dados a partir do servidor e exibe erros de validação/conflito retornados.
5. **Given** a tela de Responsável ou Administrador, **when** há solicitações `SOLICITADA`, **then** a fila vem da API e as decisões são enviadas com o ID e tipo de aprovador configurados.
6. **Given** a tela de Administrador, **when** o usuário consulta salas, **then** os dados vêm da API e são somente leitura; a tela não simula alteração de cadastro sem endpoint correspondente.
7. **Given** dados da API indisponíveis ou inválidos, **when** uma consulta ou operação falha, **then** a interface apresenta estado de carregamento/erro e permite tentar novamente, sem substituir falhas por dados demonstrativos.
8. **Given** qualquer perfil e tamanho de tela, **when** a interface é utilizada, **then** o layout permanece responsivo e as validações/indisponibilidades apresentam mensagens claras.
9. **Given** a integração sem autenticação real, **when** IDs e tipos são configurados no navegador, **then** a interface informa que esses valores não comprovam identidade e não devem ser considerados controle de acesso.

## Dev Notes

- A integração usa a mesma origem `/api` do backend. Autenticação real e CRUD administrativo continuam fora do escopo; os IDs configurados no navegador não comprovam identidade.
- O repositório tem configuracao Maven (`pom.xml`), classe de inicializacao Spring Boot e testes Java. O checkout local usado nesta execucao esta desatualizado em relacao a `origin/main` e nao continha esses arquivos; a validacao Maven foi feita com a configuracao de `origin/main` e as alteracoes desta integracao aplicadas numa copia temporaria.
- `StatusSala` possui exatamente `DISPONIVEL`, `RESERVADA` e `EM_MANUTENCAO`. O último estado indica que novas reservas estão indisponíveis. [Source: `src/main/java/br/com/projeto_qualidade_software/projeto/enums/StatusSala.java`]
- `StatusReserva` possui `SOLICITADA`, `APROVADA`, `EM_USO`, `CONCLUIDA`, `REJEITADA`, `CANCELADA` e `NAO_COMPARECEU`. Aprovação e rejeição se aplicam a reservas `SOLICITADA`. [Source: `src/main/java/br/com/projeto_qualidade_software/projeto/enums/StatusReserva.java`; `src/main/java/br/com/projeto_qualidade_software/projeto/entities/Reserva.java`]
- A entidade `Sala` contém identificador, capacidade e estado. Não há nome ou localização definidos pelo modelo. Evitar sugerir que campos adicionais são persistidos; identificadores amigáveis apresentados no protótipo são apenas dados demonstrativos. [Source: `src/main/java/br/com/projeto_qualidade_software/projeto/entities/Sala.java`]
- A identidade visual solicitada é SENAC: azul, laranja e branco. Usar cores como apresentação visual; não há tokens oficiais de marca registrados no repositório.
- Requisitos relacionados: RF06, RF07, RF10, RF11 e RF17; RN01, RN04 e RN05. [Source: `docs/prd/requisitos-funcionais.md#3-reservas-e-alocacao`; `docs/prd/requisitos-nao-funcionais.md#evidencias-e-ferramentas-exigidas-pela-disciplina`]
- Não foram encontrados documentos de arquitetura, coding standards, tech stack, source tree ou estratégia de testes configurados em `core-config.yaml`. O código frontend deve seguir os padrões já existentes do Spring Boot e manter validações compatíveis com as ferramentas disponíveis, sem introduzir dependências de build não solicitadas.
- Não há epic local ou integração ClickUp disponível neste repositório; esta é a primeira story local (1.1), criada a partir do escopo solicitado e do PRD existente.

### Completion Notes List

- No escopo original da story, foram implementadas as três telas e interações em HTML, CSS e JavaScript vanilla, inicialmente com dados demonstrativos.
- Os estados de sala e reserva continuam sincronizados com os enums Java. `EM_MANUTENCAO` bloqueia novas solicitações e impede a aprovação de pedidos pendentes daquela sala.
- O solicitante autorizou a integração do protótipo com a API; a autenticação e o CRUD administrativo permanecem fora deste escopo.
- Adicionadas listagens de salas/reservas, cliente HTTP e chamadas da interface, além da rota compatível `/api/reservas/pendentes`.
- A listagem de salas usa `SalaService`, mantendo o padrão de camadas da aplicação e permitindo os testes MVC existentes.
- Validação: 156 testes Maven passaram (0 falhas/erros) com JDK 21, além de 15 testes Node.js, verificações sintáticas JS, validação YAML e `git diff --check`.
- Como o checkout local `main` está 19 commits atrás e não contém o POM nem os testes Java, a suíte Maven foi executada numa cópia temporária de `origin/main` com as alterações Java do trabalho aplicadas; a cópia e o banco temporários foram removidos.
- Os fluxos REST de listagem, criação, consulta por solicitante, alteração, aprovação, cancelamento e rejeição também passaram por smoke test HTTP com PostgreSQL temporário.
